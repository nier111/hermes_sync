# 该不该把新 agent 接进编排器（agent adapter 评估）

触发：用户问「要不要把 X（Kimi Code / Gemini CLI / 新 agent …）也加进 agent-pool」
或者出现一个看起来能干的新 CLI agent 时。

## 结论模板

给出**带理由的取舍结论 + 分阶段验证方案**，不要只摆选项。用户明确不接受
「为了架构完整」而堆冗余组件（原话："太多了根本没必要，有点冗余"）。

## 判断顺序

1. **职责重叠**：新 agent 与已有 agent 的定位是否几乎相同？
   案例（2026-09）：Kimi Code ≈ Codex，都是编程执行器 → 重叠度高。
2. **缺口 vs 冗余**：它补的是「能力缺口」还是「额度冗余」？
   额度兜底用官方 CLI 独立顶着就行，**不需要 adapter**——adapter 是为日常调度服务的，
   不是为备份额度存在的。
3. **接入真实成本**（每一条都是要长期还的债）：
   登录与额度体系、会话恢复参数、看门狗分层超时、输出/流式协议适配、
   UI 里"这个任务该派给谁"的判断成本、版本升级后的回归。
4. **验证门槛**：先用官方 CLI 独立跑真实任务 20-30 轮，重点看它能否可靠续接
   主力额度断粮后的工作链（长上下文不丢约束、不乱改文件、工具调用可靠）。
   过了这关再写 adapter。
5. **窗口算进并发**：订阅套餐的 5 小时窗口/高峰限流直接决定"能同时跑几个 agent"。
   行情与复核方法见 `api-cost-forensics` → `references/cn-llm-subscription-plans.md`。

## 报价前的复核（避免给出过时建议）

- 官方定价页 + FAQ/**migration** 三页一起看；口径变更（按请求 → 按 token）几乎只写在
  migration 页，搜索摘要和第三方对比站常把新旧口径混着说。
- 厂商文档站是 JS 渲染 SPA：browser_exec 多 session 并行打开，
  `js("document.body.innerText")` 读渲染后全文，比 web_extract 稳。
- 用户说「官方不会明说 / 继续搜没意义」时**立刻停止找证据**，转为讲机制
  （模型路由、推理预算、快速路径），别拿公关文案证明公关文案。
