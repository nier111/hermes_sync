# 订阅套餐（Token Plan / Coding Plan）配额核实与购买建议

> 核实日期 **2026-09-19**。与 `references/cn-llm-subscription-plans.md` 同属一个主题：
> 那份是行情速查（价格 / 窗口 / 模型 ID），**本文件是「怎么给用户下购买建议」的方法论 + 本次核实到的官方数字与风险证据**。
> 两者数字若冲突，以本文件（更新）为准，并顺手把旧文件补正。

## 0. 触发场景

用户问「X 家会员一个月多少 token / 值不值得买 / 我是不是被坑了」，
或你要在对话里推荐某个 LLM 套餐（无论是替用户省钱还是替他选模型）。

## 1. 铁律：没有官方配额数字，就不给购买建议

- 官方页面查不到精确配额时，**直说查不到**；不要用「看起来额度不少」「网上都说不心疼」当依据。
- **禁止跨厂商类推**。2026-09 的真实教训：把 MiniMax Ultra 的「71 亿」串到了 Kimi Plus 上，
  用户据此买了 ¥99 Kimi Plus 会员，实测 20 分钟就把 5 小时桶打满。事后回查，
  Kimi 官方**从未公布 Plus 的 token 总量**。
- **来源必须分级标注**，混用即是错误：

  | 级别 | 例子 | 可写的措辞 |
  |---|---|---|
  | 官方公布 | 订阅页写「月度约 6 亿+ token M3 用量」 | 可以直接引 |
  | 第三方整理 | codingplan.fyi、公众号实测贴 | 「第三方整理，未在官网页确认」 |
  | 本地实测反推 | 本机 usage ÷ 后台百分比 | 「按 X 口径约 Y，不成立条件：…」 |

- 反推值必须**附上成立条件**。例：Kimi「4.11% → 约 0.97 亿 token」只在
  cache_read 与普通输入 1:1 扣、输出/推理无特殊权重、失败请求不计费、本地调用数≈服务端请求数时成立。
- 结论给区间与不确定性，**不给「放心买，肯定用不完」这类担保**。

## 2. 推荐顺序（最小可验证单元优先）

```text
1. 最小可验证单元：最低档月付，或干脆只买小额积分包（不订套餐）
   → MiniMax：¥30 / 4,489 积分，1 年有效，可不订 Token Plan 单独买
2. 干净隔离会话实测（不要挂在常驻长会话 / 主 agent 会话上）
3. 确认 5h 与周窗口真实扣法后，再决定续订或升级
```

禁止：年付、自动续费、把新套餐直接接给常驻长会话。
理由：按 token 计费后**长会话的 cache_read 每轮累加**，是额度杀手；
年付/自动续费把「一个月的实验」变成「一年的绑定」，而订阅制普遍不支持退款。

实测协议：
- 新建干净会话，初始上下文控制在几千 token（别继承十万级上下文）；
- 跑一个真实小任务，每 10-20 次调用采一次额度；
- 同时记录 input / cache_read / output，先分清是「真在干活」还是「卡住的循环在烧钱」。

## 3. 官方配额速查（2026-09-19 从官方订阅页读到，非搜索摘要）

### MiniMax Token Plan — 月度 token 量只写在订阅页

`https://platform.minimaxi.com/subscribe/token-plan`（pricing 文档页**没有**这些数字）

| 套餐 | 月付 | 年付 | 官方月度 M3 用量 | 按单次 ~50K 估算 | M2.7 5h 参考 |
|---|---:|---:|---:|---:|---:|
| Plus | ¥49 | ¥490 | 约 **6 亿+** token | 约 12,000 次 | 1,500（highspeed 750） |
| Max | ¥119 | ¥1,190 | 约 **18 亿+** token | 约 36,000 次 | 4,500（highspeed 2,250） |
| Ultra | ¥469 | ¥4,690 | 约 **71 亿+** token | 约 140,000 次 | 15,000（highspeed 7,500） |

- 单位价格：Plus ≈ ¥81.7 / 十亿 token，Max ≈ ¥66.1，Ultra ≈ ¥66.1 → **Max 起才划算**。
- 窗口三层：**5 小时固定窗口 + 周窗口 + 月度池**，未用完不结转。达到上限只能：买积分 / 升级 / 换按量 Key / 等重置。
- **M3 的 5h token 上限与周上限官方从未公布**，只公布 M2.7 的参考次数 → 必须实测。
- 积分包：¥30 → 4,489；¥150 → 22,460；¥500 → 74,900（1000 积分 = ¥7，与 API 目录价 1:1）。
- 查用量：`GET https://www.minimaxi.com/v1/token_plan/remains`。
- 限流：高峰（工作日 15:00-17:30）动态收紧，Plus 约 3-4 个 Agent。
- 订阅制不支持退款。

### Kimi Plus — 月池无官方 token 数字

- 官方只写「5 小时滚动频控 + 月度额度池，按 token 扣减」，**从不给 Plus 的 token 总量**；后台只显示百分比。
- 公开可用的唯一硬事实：**5h 桶 ≈ 46 次十万上下文级重型请求**（本机 OpenClaw 实测，20 分钟打满）。
- 反推（**不可当官方值**）：399 万 input+cache ÷ 4.11% ≈ 0.97 亿 token 当量。

## 4. 额度异常消耗证据（下单前必查）

厂商 GitHub 官方仓库的 issue 是唯一能拿到「真实扣减行为」的地方。
搜 `<vendor>/<model>` 仓库 + `quota` / `billing` / `cache_read` / `exhausts` 关键词。

MiniMax 已知问题：
- `MiniMax-AI/MiniMax-M3#25`：Plus + M3 + Anthropic-Messages 端点，**40 回合 / 17 分钟**消耗
  8,182,111 token，其中 `cache_read` 7,964,672（**97.3%**），新增未缓存输入仅 20.7 万；
  约吃掉 8% 的 5h 窗口 → 反推 5h 桶约 1 亿 token 当量（非官方）。
  `cache_read` 逐轮单调增长（每轮 +2~3k），疑似 thinking 块及其 base64 signature 被算进缓存前缀并逐轮重放。
- `MiniMax-AI/MiniMax-M3#16`（2026-06-08 开）：中文用户报告周总额与 5h 消耗突然异常加快，官方长期零回复。
- `MiniMax-AI/MiniMax-M2.7#47`：`remains_time` 在**零请求时也持续减少**（24 秒掉 23,589 ms），
  像倒计时而非用量计；同页报告 Plus 在 Claude Code 连续 agentic 工作下 4-5 小时耗尽。
- 钛媒体汇总：旧模式 Plus 5h 约 1,500 次，改按 token 后实测仅支撑约 300-500 次；同时新增周限额。

结论模板：**月池大 ≠ 短窗口耐用**。给建议时要把「月度容量」和「5h/周窗口」分开讲，
并明确说清哪个数字是官方的、哪个是反推的。

## 5. 抓取技巧

- 文档站是 JS 渲染 SPA；用 browser_exec 起独立 session 打开，`js("document.body.innerText")` 读渲染后全文。
- **文档页加 `.md` 后缀常能直接拿 markdown 全文**（如 `.../guides/pricing-token-plan.md`），比爬 SPA 省事。
- 订阅页（`/subscribe/...`）是唯一写月度 token 量的地方，必须用 browser 真实打开；
  `web_extract` 对订阅页常返回残缺内容。
- 搜索摘要会把新旧计费口径混着说，**不可信**；一律回官方页确认。
