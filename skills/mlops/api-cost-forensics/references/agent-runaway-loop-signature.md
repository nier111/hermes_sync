# 订阅额度被"烧穿"的诊断：runaway agent loop 特征

> 场景：用户不是收到账单，而是说「我的 xx 套餐 5h 额度 20 分钟就没了」。
> 结论几乎总是 **agent 在循环重发巨大上下文**，而不是模型贵。
> 本文件给可复用的判定特征与归因拆分；测量脚本见 skill `openclaw-interop`
> 的 `scripts/openclaw-session-usage.py`。

## 1. 为什么"按 token 计费"的套餐会被瞬间吃穿

Flat-rate / coding plan 的窗口额度按 **实际 token 消耗** 扣（不是按请求次数）。
而 agent 的每一轮工具调用都要把 **整段会话上下文重发一次**。所以：

    drained_tokens ≈ Σ_calls (input + cacheRead)

一次调用的口径不是"新读进来多少"，而是"这一轮总共发了多少"。长会话里
`cacheRead` 往往比 `input` 大一到两个数量级 —— 只看 `input` 会把量级估错 50 倍。

推论：**成本对会话长度是超线性的**。同一个探索任务跑在 8k token 的新会话里和
跑在 120k token 的 main 会话里，价格差十几倍。这是给用户的核心建议之一。

## 2. Runaway loop 特征（一眼认出没干活的那段）

逐次调用（按 `created_at`）排开，找这种模式：

- 调用间隔**像节拍器**（实测 18.5 秒/次，连续 14 次）
- `output` 每次**完全相同**（实测恒定 1178 token）
- `input` 每次只涨几个 token（实测 +3/次），`cacheRead` 每次固定 +1280
- 连续多轮，直到被人为打断

这三点同时出现 = 同一个响应被原地重放，不是在做新工作。上面那 14 次占到整个
session 消耗的 **42%**，3 分 41 秒，产出为零。

对照：**真干活**的段落 `output` 会上下波动（几百到几千），`input` 也有实质变化。

## 3. 实测标定值（2026-09-19，Kimi Code Plus / `kimi-for-coding`）

单次 5h 窗口 ≈ **400 万 input token** 量级 → 37 次本地记录调用（Kimi 侧显示 46 次）
→ 输出仅 3.2 万 token。拆开是：

| 段落 | 时长 | 调用 | 消耗 | 性质 |
|---|---|---|---|---|
| 找模型 / 翻 key | ~10 min | ~20 | ~2.3M | 真干活，但跑在 100k+ token 的 main 会话里 |
| QQ 自回声循环 | 3.5 min | 14 | ~1.7M | 纯浪费 |

**本地记录数 ≠ 平台请求数**：本地 37 vs 平台 46。差额解释为「失败/中止但照样计费
的请求」是**推测**，要么去平台控制台核对，要么明说是推测 —— 不要断言。

## 4. 归因拆分（这部分决定建议，别笼统说"agent 就是费"）

按这个顺序拆，每条对应不同修法：

1. **长上下文放大** → 探索类/翻数据库类任务开新会话或丢 subagent，别在 main 会话跑。
2. **真 bug 循环** → 看到重复话术立刻打断；3 分钟能救回近一半额度。
3. **模型/口径选择** → 换模型、关高上下文档（如 1M 上下文档约为 256k 档的两倍消耗）。
4. **套餐本身太小** → 只有在 1-3 都排除后才说这句，否则等于替厂商背锅。

用户会追问逻辑链条，所以每一步都要有可指向的证据（哪张表、哪几行、什么时间）。

## 5. 顺带要检查的副作用

Agent 在"自查凭证"这类任务里会：

- 把整份 state/agent SQLite **复制到 `/tmp`** 再查（含明文 API key，且经常忘了删）
- 让 provider key 明文落进 gateway 的当日日志

处理：按 key 前缀 grep `/tmp` 和日志，把结果和清理建议一起报给用户
（这是低风险但该说的卫生问题，不要跳过）。
