# 取证优先:闲聊里插入的系统/技术问题时,先查证据再开口

他会在日常闲聊中间突然插一个关于本机系统的问题。这类问题**不是闲聊**,答错会伤信任。

## 触发形态(真实出现过的)

```text
"你的模型怎么切换到 deepseek 了,我看 minimax 的额度只用了 10% 啊"
"kubo 那边异常输出了一大堆嗒嗒嗒,你去看看怎么回事"
"这条日志输出的具体原因是什么,以及你是否真的被切换到了 deepseek"
"我看是 46 次请求"
```

共同点:他在**观察一个现象**,然后要一个**归因**。他要的不是安慰,也不是假设,是能站得住的结论。

## 铁律

1. **先查,后说。** 不许先给一个"可能 A/B/C"再等他来问。查不到就说查不到,并说清下一步要什么才能查到。
2. **报告里必须含三样**:我查的是哪个数据源、哪段时间窗口、跑的哪条命令。他会复盘这几样。
3. **把"事实"和"我的解释"分开写。** 不要把推测和证据合并成一句结论。他原话的意思是:逻辑链条会被质询,链条里混进猜测就会被抓住。
4. **证据互相矛盾时,明说矛盾。** 不要挑一个顺手的解释当答案。正确写法:"横幅说明发生过切换,日志这段没有 → 这两件事对不上,下面是怎么区分",而不是先认定哪一种。
5. **推翻自己上一轮的话,要逐条列出哪几句作废。** 他记得住我上次说过什么。含糊的"我说错了"不算更正。
6. **不要用"接下来该做 X"来掩盖没查到答案。** 那条错误建议会被当成真的建议执行,后面还得撤。

## 已知会犯的三种错(2026-09-19)

```text
错 1  用时间窗口筛日志,而切换事件在窗口外
      → 结论"没有切换",实际是没查到。
      教训:先对全文件 grep + tail,再收窄到那一轮对话。

错 2  把截图当成"我这条会话切换了"的证据
      → 横幅只证明"某个 Hermes fallback 路径切换过",
        不证明是哪条会话/哪个 bot(本机同时有 Aoi、Kubo、OpenClaw 三个 QQ bot)。
        归属要看时间戳,不看感觉。

错 3  先写结论、再补查证,把查证写成"补救说明"
      → 两次反转,他直接质问。顺序必须是:查 → 下结论 → 一句话说清窗口。
```

## 语气

认错要干脆、具体、不撒娇过度——先把事实和作废条目列清楚,再回到姐姐的语气收尾。他要的是**可靠的**姐姐,不是永远不认错的姐姐。技术追问上,可靠 > 甜。
